## Current Fusion Spec Boundary

The current fusion-spec completion matrix is stricter than this milestone gate history. It tracks current gaps by product area and is the source of truth for whether a new full-project completion claim is valid.

- Phase 30 baseline: `scripts/verify-commercial-completion.sh` passed for the 2026-05-29 repository state with deploy validation, backup/restore smoke, DB-backed backend journey, browser journey, docs, Relay security, and no environment skips.
- DB-free local proof: route-surface, CSRF/auth, OpenAPI contract, fake-store, and fake-provider tests may prove deterministic handler behavior without `TEST_DATABASE_URL`. Recent subscription, top-up, and paid Marketplace checkout-creator failure tests belong in this class.
- DB-backed proof: SQL persistence, cross-tenant lifecycle, admin inspection, payout, settlement, and webhook idempotency claims require `TEST_DATABASE_URL`-backed tests in CI or a recorded target environment. Local skips are allowed only under the policy below and cannot upgrade persistence claims by themselves.
- External deployment/payment proof: live payment-provider credentials, external payout rails, production telemetry, Kubernetes/runtime validation, and backup/restore proof remain environment-specific. They are not inferred from fake provider tests, local static checks, or an old strict-verifier run.

## Claim Rules

- A milestone may claim completion only for requirements whose current repository evidence, automated verification, and required runtime smoke are recorded.
- A new full-project or commercial-complete claim after post-Phase 30 hardening requires closing the current fusion-spec matrix gaps and rerunning the strict verifier without environment skips.
- DB-free tests may close local route, contract, CSRF/auth, validation, and fail-closed handler gaps; DB-backed lifecycle and persistence claims still need `TEST_DATABASE_URL` evidence.
- External deployment/payment claims must name the target environment, provider configuration, command, pass/fail result, skipped checks, and residual risk.
- v04 Commercial Foundation may claim tenant/security/migration/CI foundation completion after `CI-01` and `DOC-03` pass.
- v04 must not claim final commercial readiness or commercial completeness.
- v07 is complete and v08 Product Completeness is complete only for the Phase 30 baseline after strict verification; a current commercial release cannot inherit that claim without fresh target/live evidence and a no-skip strict verifier run.
- v05 may claim Relay Authority Gate completion only after route classification, production fail-closed, provider-bypass checks, endpoint auth/rate-limit/audit, settlement/refund behavior, and v05 Relay Authority Gate closeout evidence all pass.
- When Relay Realtime commercial lifecycle is enabled for a final target release, abort-settlement proof must come from explicit `realtime_usage_missing` terminal usage records; generic `upstream_error` usage rows are ordinary provider-failure evidence and do not satisfy the Realtime abort proof.
- v06 may claim Billing And Monetization Gate completion only because subscription lifecycle, top-up fulfillment, refunds, invoices, failed-payment states, plan changes, Marketplace settlement, payout state, moderation workflows, admin billing inspection, and v06 closeout evidence have all passed Phase 17-20 verification.
- v07 may claim Operations Gate completion only after orchestration runtime proof, backup/restore smoke, observability, alerts/dashboards/SLOs, release/rollback runbooks, incident/DR runbooks, and v07 closeout evidence all pass.
- v08 may claim `PROD-01` only after default built-in Agent tools are proven real or disabled by tests, docs, and quality gates; `web_search` and `http_request` cannot be counted as commercial-ready while disabled by default.
- v08 may claim `PROD-02` only after durable Agent workflow schema, service state transitions, status APIs, approval/reject/retry behavior, memory evidence, failure evidence, and cross-tenant denial tests pass with DB-backed evidence.
- v08 may claim `PROD-03` only after Knowledge ingestion stores Relay-produced embeddings, retrieval uses pgvector vector search under organization scope, API/UI results expose source citations, and `.planning/phases/27-knowledge-product-promise-alignment/27-VERIFICATION.md` records backend, frontend, docs, and diff evidence.
- v08 may claim `PROD-04` only after active Chat, Agent/SOLO, Knowledge, Admin, and Marketplace journeys have focused frontend tests for commercial loading/error/empty/action states, quota or budget context, review and settlement boundaries, docs gates, and `.planning/phases/28-commercial-ux-and-journey-hardening/28-VERIFICATION.md`.
- v08 may claim `PROD-05` only after README, public docs, onboarding, pricing, operator guides, API docs, architecture contracts, commercial gates, quality gates, stale-doc scans, and `.planning/phases/29-public-docs-onboarding-pricing-and-operator-guides/29-VERIFICATION.md` prove alignment with implemented tenant, Relay, billing, Marketplace, operations, and product behavior.
- v08 may claim `PROD-06`, `AUDIT-01`, Product Completeness Gate, and final commercial readiness only after `scripts/collect-target-release-artifacts.sh` has collected strict verifier, deployment, Kubernetes, workflow telemetry, request-log observability, RAG, Relay, Marketplace, provider runtime config, Stripe/Alipay/WeChat Pay live rail, gRPC smoke, secret audit, and microservice database artifact bodies for the filled target manifest; `scripts/compute-target-release-digests.sh --write` or `npm run verify:target-release:digests -- --write` has refreshed canonical target evidence and artifact bundle digests; `scripts/verify-commercial-completion.sh` then passes with deploy validation, Kubernetes validation, backup/restore smoke, and target live evidence manifest validation enabled, no `COMMERCIAL_COMPLETION_ALLOW_ENV_SKIPS=true`, `OBLIVIOUS_TARGET_EVIDENCE_FILE` pointing at that filled manifest, `OBLIVIOUS_TARGET_ARTIFACT_DIR` set to the downloaded artifact bodies for strict target evidence validation, and `.planning/phases/30-end-to-end-commercial-journey-and-final-audit/30-VERIFICATION.md` records exact command evidence.
- `scripts/assemble-target-release-evidence.sh --artifact-dir /path/outside/git/downloaded-artifacts --validate` may be used after digest refresh as an earlier fail-fast check that the assembled manifest still matches downloaded artifact bodies; it does not replace the final no-skip `scripts/verify-commercial-completion.sh` run.
- `scripts/verify-target-release-evidence.sh --manifest-only` is only a non-final manifest lint mode. The default verifier invocation requires `OBLIVIOUS_TARGET_ARTIFACT_DIR` and downloaded artifact bodies for final target evidence validation.
- Deployment and Kubernetes target proof must be production-bound artifact-body evidence, not pass-only JSON. Deployment proof requires `targetEnvironment=production` plus concrete deploy validation, backup/restore, and migration replay references. Kubernetes proof requires `targetEnvironment=production`, `clusterRef`, `namespace`, `secretFileClass=external-filled`, and concrete validation, rollout, and failover references, without embedded secret material.
- Request-log latency SLO target proof must carry concrete alert-delivery and recovery-audit IDs. `sample`, `fake`, placeholder, or secret-like `lastDeliveryId` and `lastRecordId` values are not valid final evidence.
- Provider runtime config target proof must include per-provider details for Stripe, Alipay, and WeChat Pay. Summary counts alone are insufficient; each provider must report live environment, external-filled checkout base URL class, webhook route proof, webhook verification proof, provider env proof, and a concrete evidence ID.
- Microservice database target proof must include per-service details for relay, chat, workflow, rag, agent, billing, marketplace, admin, channel, task, and observability. Summary counts alone are insufficient; each service must report an external-filled database URL class, migration readiness proof, and a concrete evidence ID.
- Relay Batch final target proof must report `commercial_lifecycle_enabled` with `prebillReservation`, `pollingCompletion`, `settlement`, `refund`, and `usageAudit` all passing. The Batch proof summary must include positive `usageAuditRecords` and `requestLogAuditRecords`, and both counts must cover `settlementRecords + refundRecords` in the same release window. `requestLogAuditRecords` must come from allowed `relay.route_decision` request-log evidence for Batch requests.
- Provider live rail target proof must report `providerEnvironment=live` for Stripe, Alipay, and WeChat Pay, include pass evidence for checkout, refund, payout, and reconciliation, and carry non-placeholder provider references for each operation without embedding secret material.
- `.github/workflows/release-evidence.yml` can be manually triggered to re-verify a target evidence manifest and downloaded artifact-body bundle uploaded by another GitHub Actions run. This workflow refreshes canonical digests and runs target-evidence-only strict preflight, but it does not carry Kubernetes secrets, live provider credentials, deployment smoke, Kubernetes validation, or backup/restore proof; the final commercial claim still requires the no-skip `scripts/verify-commercial-completion.sh` run above.
- Any future readiness claim must link to exact files, commands, environment class, migration status, pass/fail result, skipped checks, and residual risk.
