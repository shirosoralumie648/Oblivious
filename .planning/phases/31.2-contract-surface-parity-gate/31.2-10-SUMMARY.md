## Decisions Made

- Runtime `projectionDigest` hashes `{identity,generation,capabilities}` and is recomputed from the authenticated response. Generated `releaseProjectionDigest` hashes the static `{capabilities,surfaces}` projection. They are intentionally stored and verified as separate digest classes and are never directly compared.
- Static authority comes from exact generated capability IDs/dispositions; dynamic availability comes only from the authenticated runtime response after release identity and runtime digest validation.
- Conditional direct routes and navigation use the same provider lookup. Loading, errors, 401, mismatches, blocked/disabled/unknown availability, and absent capability IDs all take the same closed path.
- Model/tool capability identities remain read-only response data. Page updates and API serializers construct business payloads explicitly and do not spread response objects.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Kept runtime and generated projection digests as distinct contract classes**
- **Found during:** Task 1 authenticated projection validation
- **Issue:** The plan interface described directly exact-matching the runtime `projectionDigest` to generated `releaseProjectionDigest`, but the established producers hash different payload classes: runtime `{identity,generation,capabilities}` versus static `{capabilities,surfaces}`.
- **Fix:** Recompute and exact-match the runtime digest against its authenticated response, expose the generated digest separately, and exact-join every returned capability ID/disposition against the generated projection.
