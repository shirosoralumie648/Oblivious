## Adversarial Reproduction

### CR-02: frontend inventory false green

A temporary copy of `scripts/testdata/frontend-surface/production` was mutated outside the repository.

| Mutation | Observed result | Required result |
|---|---|---|
| Add `const hiddenFetch = fetch; hiddenFetch(...)` and `globalThis.fetch(...)` | 12 operations, `unresolved=[]`, both calls escaped classification | Non-empty unresolved/failure unless each call resolves to one canonical operation contract |
| Replace a known literal path with `const dynamicWrongPath = '/fixture/wrong'` | 12 operations, `unresolved=[]`, wrong path accepted | `transport_path_mismatch` or another fail-closed unresolved code |

The behavior follows directly from `scripts/frontend_surface_sidecar.mjs`:

- `transportKind` recognizes direct identifier spellings and selected typed property names, not aliased symbols or `globalThis.fetch`.
- The production visitor does nothing when `transportKind` returns `null`.
- `invocationPathMatches` returns `true` for every expression that `literalValue` cannot reduce to a string.

The positive sidecar run (`127 files / 264 operations / 80 exposures`) and its existing six Node tests therefore do not prove complete transport discovery.

### CR-01: external replay false freshness

A disposable `pgvector/pgvector:pg16` container was populated with `public.customer_data` and one row, without creating `schema_migrations`. The exact preflight predicates used by the external path produced:

```json
{"connectivity":"1","schemaMigrationsExists":"false","scriptBeforeLedgerRows":0,"publicRelations":1,"preexistingCustomerRows":1,"acceptedAsFreshByCurrentCheck":true}
```

`scripts/verify-migration-replay.sh` only runs `SELECT 1` before external replay, then derives freshness from an absent or empty `schema_migrations` table. It never inspects other application objects or data. Real migrations subsequently run twice; migration `0027_tenant_scope_core_domains.sql` includes data updates/deletes. External cleanup owns neither the caller database nor a disposable schema, yet the default cleanup result remains `succeeded`.

The existing `reused_database` fixture uses a non-empty migration ledger. It does not exercise the more dangerous empty-ledger plus pre-existing-data case.
