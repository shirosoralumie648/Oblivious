<interfaces>
`Router.RouteWithBilling` performs organization `QuotaManager.Refund(ctx, organizationID, billingSessionID)` and API-token `RefundRelayAPITokenQuota(ctx, apiTokenID, amount)` after the late `requireModel` and `requireProvider` checks. Both returned errors are currently discarded. `quota.SQLStore.RefundBillingSession` already locks the billing session and owns the quota-balance transaction, while `RelayAPITokenSQLStore` owns API-token quota updates. The route must create one server-generated route-attempt identity before either quota preauthorization begins, fail closed before reservation side effects if generation fails, and carry that same identity through every reservation and late-readiness compensation branch for that attempt.

Follow the established durable patterns in `knowledge/index_job_store.go` and `relay/store.go`: commit the job before the external/effect attempt, claim due work with a transaction plus `FOR UPDATE SKIP LOCKED`, retain a lease, and persist retry state. The compensation job stores only SHA-256 job/scope digests, opaque internal organization/billing-session/API-token record IDs and amount required to refund, required/completed scope flags, attempts/timestamps, and allowlisted error codes. It must not persist the raw route-attempt identity, caller idempotency key, raw token, request/user/model/provider data, readiness text, or storage errors.

Derive the normalized job key from a canonical tuple led by the required server-generated route-attempt identity, then late-readiness stage, billing-session ID, API-token record ID, canonical amount, and caller idempotency only as non-authoritative correlation; derive each normalized scope key from that route-attempt-bound job digest plus its scope. Persist only SHA-256 digests and reject a missing route-attempt identity. Re-arming the same route attempt is idempotent, while a new route attempt always receives a new identity even when caller idempotency is empty or reused. Commit the idempotent upsert before either refund call. Organization replay uses the billing-session status as its durable effect receipt and treats an already-refunded session as success; API-token replay records the route-attempt-bound scope receipt in the same SQL transaction that decrements quota. A crash after an effect but before job-state update must therefore replay as success without applying credit twice or allowing one token-only reservation to complete/refund another.

Use Go multi-error unwrapping (`errors.Join` or an equivalent typed `Unwrap() []error`) so `releasecontract.IsReadinessCode` continues to find the primary readiness error. Compensation errors identify only stable scopes (`organization-quota`, `api-token-quota`, or `compensation-persistence`) and allowlisted operations/codes, never IDs or raw storage details.

## Scoped Exception: one coherent durability slice

This plan intentionally owns thirteen files across durable state, immediate refund effects, and the two declared Relay runtime owners. Retaining them in one plan is a scoped exception because CR-03 is one end-to-end durability invariant: a route-attempt-bound job and its receipts must be committed before a refund, used by idempotent immediate effects, and consumed unchanged by both monolith and standalone reconciliation workers. Splitting those boundaries into independently executable plans would permit a persisted job/receipt protocol that no runtime consumes, or a worker that applies a divergent effect protocol, leaving restart recovery unprovable.

Execution and atomic-commit boundaries stay explicit inside the slice:

1. Task 1 owns only the migration, durable job/receipt/lease state, store lifecycle, and state-focused tests.
2. Task 2 owns only the idempotent organization/API-token effects and the late-denial Router handoff that consumes Task 1's contract.
3. Task 3 owns only retry-worker lifecycle plus monolith and standalone construction; it consumes the persisted contract and does not redesign the migration or immediate effect semantics.

This task order keeps persistence/effect behavior independently reviewable before runtime wiring while preserving the complete CR-03 restart-recovery proof in one plan.
