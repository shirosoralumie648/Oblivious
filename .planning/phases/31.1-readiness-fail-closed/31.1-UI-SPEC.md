# Phase 31.1 - UI Design Contract

> Visual and interaction contract for the Phase 31.1 gap closure. Generated by the generic-agent workaround for `gsd-ui-researcher`; verify with `gsd-ui-checker` before execution.

---

## Scope Fence

This gap closure does not add a page, navigation item, dashboard band, marketing surface, or visual redesign. The canonical verification gap is in the server projection behavior: Admin and App responses must not advertise old capability values as enabled when the current evaluation is stale or unavailable. No current frontend production caller consumes `/api/v1/admin/readiness` or `/api/v1/app/readiness/capabilities`; authenticated app-wide projection wiring remains Phase 31.2.

Permitted frontend work is limited to preserving the existing read-only `capabilityId` contract in model/tool response normalization and tests if backend contract repairs require it. Existing Chat, Agent, and Admin layouts, spacing, colors, typography, and component composition remain unchanged. A backend-only gap plan satisfies this UI contract when it proves the state semantics below and introduces no frontend churn.

## State And Interaction Contract

| State | Admin contract | App/model/tool contract | Action contract |
|-------|----------------|-------------------------|-----------------|
| Loading | Preserve the current layout and render existing skeleton geometry; do not render prior rows as current. | Selectors and capability-dependent commands remain disabled; do not fall back to hard-coded models/tools. | No side-effect command is enabled while authority is unknown. |
| Fresh and enabled | Show `Enabled` with generation/time context when an Admin inventory is eventually wired. | Include only a server-returned, currently enabled subject. | The normal command may be enabled, but runtime remains the final authority. |
| Fresh and disabled | Keep the Admin row visible with `Disabled`, sanitized reason code, dependencies, and remediation when supplied. | Omit from a new-choice list. If already persisted/selected, render it as unavailable rather than silently replacing it. | Disable the affected command and expose a short textual reason. |
| Fresh and blocked | Keep the Admin row visible with `Blocked`; do not collapse it into an empty state. | Do not offer as selectable or executable. | Disable the affected command. Retrying reloads server state; it never toggles readiness locally. |
| Stale evaluation | No capability may render as enabled. A server error response produces the full error state; a forced-disabled response may retain rows only as non-actionable diagnostics beneath one stale banner. | Clear current choices from actionable option sets. A persisted value may remain visible only as a disabled sentinel labelled `Unavailable`. | All capability-dependent commands remain disabled until a fresh server projection is received. |
| Unavailable / identity mismatch | Do not reuse last-good inventory as current truth. Show a sanitized error without raw probe payload, endpoint, credential, or secret material. | Empty the actionable projection. Do not use cached `capabilityId`, catalog entries, or selector state to re-enable controls. | `Retry readiness check` performs a new GET only. No optimistic enablement and no local override. |
| Empty but fresh | Distinguish a valid empty result from an error. | Show no selectable capabilities. | No capability-dependent command is available. |
| Recovery | Replace the stale/error state only after a successful response with a newer/current valid generation. | Rebuild choices from that response; do not merge stale and fresh arrays. | Focus remains on the retry control while loading, then returns to the affected selector/section without a page jump. |

Per locked decision D-RDY-04, `now == validUntil` remains fresh. Staleness begins only when `now > validUntil`; at `validUntil + 1ns`, presentation fails closed at the same boundary as the server. There is no grace interval, countdown-based local extension, cached-generation pinning, or frontend freshness calculation. Admin and App projections return an error or contain zero `enabled: true` rows only after this boundary.

## Capability Identity Contract

- `ModelOption.capabilityId` and `AgentToolDefinition.capabilityId` are required server response metadata. Preserve the exact string through typed response normalization and presentation state; do not synthesize, trim into a different value, remap, or infer it from model/tool names.
- A missing or blank response `capabilityId` is an invalid payload. The affected selector/catalog enters its unavailable error state and exposes no actionable fallback.
- `capabilityId` is not user-editable and must not appear in an input, hidden form field, URL parameter, local preference, persisted draft, create request, or update request.
- Agent tool mutation serializers continue to omit `capabilityId`. Chat/model mutations submit the business subject selected from the response, never capability authority.
- Admin inventory may eventually display capability IDs as non-editable monospace diagnostics. App selectors do not need to display them.
- Capability metadata may be used to exact-join a fresh server projection with a server-returned catalog response, but it never authorizes an effect. The next server mutation/execution still re-resolves current authority.
- Do not use `capabilityId` alone as a React list key when several model/tool subjects can share one capability; keep the stable business subject key while retaining capability metadata on the item.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | `Retry readiness check` |
| Empty state heading | `No capabilities are currently available` |
| Empty state body | `Available models and tools will appear after the server reports a fresh readiness state.` |
| Stale state | `Readiness data expired. Retry before using these capabilities.` |
| Unavailable error | `Readiness is unavailable. Retry to request the current server state.` |
| Disabled item | `Unavailable` followed by a sanitized reason when the response supplies one |
| Destructive confirmation | None; this phase defines no destructive UI action |

`Retry readiness check` means reload the current server projection. It must not imply that the browser refreshes dependencies, changes a capability, or overrides a readiness verdict. Do not expose raw reason strings as the only customer-facing sentence; Admin may show stable reason codes separately for diagnosis.

## Accessibility And Responsive Behavior

- Loading containers use `aria-busy="true"`; errors use `role="alert"`. Status changes that follow a retry use the existing polite live-region pattern if one is present, without repeated announcements during periodic background loads.
- Disabled capability controls use the native `disabled` attribute. Their visible reason remains outside the disabled control so keyboard and screen-reader users can perceive it.
- `Enabled`, `Disabled`, `Blocked`, `Stale`, and `Unavailable` are always written as text. Existing semantic dots are supplementary and `aria-hidden`.
- A retry control uses the existing Remix refresh icon plus the text `Retry readiness check`; the icon is `aria-hidden`.
- On narrow screens, status metadata wraps below the subject label. Capability IDs and reason codes use `overflow-wrap:anywhere`; they never force horizontal page scrolling or overlap an action.
- Existing table/panel/card radii stay at 8px or the detected shadcn token. Do not add nested cards for readiness states.

---

## Verification Contract

The gap-closure plan must prove these behaviors without requiring a visual redesign:

1. Boundary tests prove `now == validUntil` remains fresh and `now == validUntil + 1ns` is stale. Admin and App projections return an error or contain zero `enabled: true` rows only for the latter, after-boundary case.
2. Unavailable, stale, identity-mismatched, and missing-authority responses cannot produce actionable model/tool choices.
3. A retry cannot locally convert a disabled capability to enabled and cannot merge a stale array into a fresh generation.
4. Existing model/tool response tests preserve exact server `capabilityId`; mutation payload tests prove the field is absent.
5. No frontend production caller, new route, provider, navigation item, or readiness dashboard is added in Phase 31.1 gap closure. That integration remains Phase 31.2.
6. If no frontend implementation file changes, the planner records this UI contract as satisfied by backend response tests plus unchanged capability identity tests; screenshots and visual-regression work are not required.
