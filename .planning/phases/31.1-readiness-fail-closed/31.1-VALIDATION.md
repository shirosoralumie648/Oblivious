## Test Infrastructure

| Property | Value |
|---|---|
| **Framework** | Go `testing` + race detector, HTTP/gRPC fakes, shell/Python negative fixtures, Docker Compose/Kubernetes static validation |
| **Config** | `src/server/go.mod`, authored release contract from Phase 31, existing `scripts/verify-*.sh` conventions |
| **Quick command** | `bash scripts/verify-readiness-contract-fixtures.sh` |
| **Non-vacuous Go helper** | `scripts/run-go-tests-matched.sh` delivered by Phase 31 foundation |
| **Focused Go command** | `bash scripts/run-go-tests-matched.sh -- ./internal/releasecontract -run '^TestReadinessManagerContract$' -count=1 && bash scripts/run-go-tests-matched.sh -- ./internal/http -run '^TestReadinessControlPlaneContract$' -count=1` |
| **Full phase command** | `bash scripts/verify-readiness-contract.sh && bash scripts/verify-readiness-deployment-harness.sh` |
| **Feedback target** | package/fixture feedback under five minutes; container harness runs as a separate committed gate |

The required helper contract is `bash scripts/run-go-tests-matched.sh -- <one package> -run <anchored top-level suite> <flags>` from the repository root. It first lists matching tests and fails unless that required package contains the exact suite, then executes under `src/server`. A row covering multiple packages chains one invocation per package; broad package globs and OR-regex existence checks are not evidence. The suite owns table/subtests for all behaviors named in its row. Phase 31.1 planning must reconcile this command with the live Phase 31 helper before execution; it may not fall back to raw targeted `go test -run`.

## Sampling Rate

- **RED/GREEN per behavior:** first run the named narrow test and observe the expected failure, implement the minimum behavior, rerun to green.
- **After every task:** run its automated command plus the directly affected package tests and `git diff --check`.
- **After every wave:** run `bash scripts/verify-readiness-contract.sh`; waves touching deployment also run static deployment validation.
- **Stage A during development:** run identity-independent behavior and identity substitution in temporary clean Git fixtures; the product worktree may be dirty and cannot produce a release pass.
- **Stage B after identity-bearing commit:** run binary/OCI/packaged-contract/runtime-audit identity checks against the exact clean `HEAD`; do not push that commit until Stage B passes, and invalidate the result after any new commit.
- **Before phase verification:** run the full phase command, focused race suite, existing quality gate and scope/claim scans from the exact clean committed checkout.
- **No skip conversion:** missing Docker/DB can shorten local feedback only; it cannot satisfy or skip the committed harness row.

## Manual-Only Verifications

None. Every Phase 31.1 completion criterion is repository-local and must have automated proof. Manual inspection may aid diagnosis but cannot replace the committed evaluator, zero-call, deployment or harness gates.

Target cluster deployment, live Provider/payment/storage checks, real customer journeys and signed artifact verification are deliberately absent; they belong to later phases and cannot be manually signed off here.

## Evidence Boundary

- Unit/fixture output is E1; the disposable monolith runtime/harness is E2.
- Every final result records environment/tool versions, release commit/tree, contract digest, profile, generation, audit digest, migration state, commands, pass/fail, skips and residual risk.
- Identity-bearing completion additionally records Stage A fixture result and Stage B exact clean `HEAD`; only that passing commit may be pushed.
- A committed check with any non-empty skip fails.
- Docker or DB unavailable means the full phase gate failed; narrower tests can still be reported separately without a phase-complete claim.
- Phase 31.1 cannot claim target deployment, non-monolith parity, E3/E4, signature/provenance, Phase 32-37 business closure or final commercial readiness.
