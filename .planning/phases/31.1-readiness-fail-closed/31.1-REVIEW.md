# Phase 31.1: Code Review Report

## Summary

Phase 31.1 is not ready to close. The review found nine production correctness or fail-closed gaps and five warnings across the exact 88-file plan union. The most consequential gaps are missing production effect-coverage proof, strict runtime composition that omits required readiness carriers, Relay paths that either bypass or over-apply model authorization, and canonical deployments that cannot become ready without the test harness.

Repository-local verification run during review:

- `cd src/server && go test ./internal/releasecontract ./internal/http ./internal/relay ./internal/agent ./internal/mcp ./internal/admin -count=1` passed.
- `bash scripts/verify-readiness-deployment-contract.sh` passed its three mutation checks.
- `git diff --check` passed before this report was written.

Those checks do not exercise the production composition and multi-provider cases below. The Docker harness, full Phase gate, target environment, migrations, and target/live evidence were not run; no readiness claim beyond repository-local review is made.

## Critical Issues

### CR-01 - Effect coverage is token-based, optional-authority, and absent from the release gate

**File/line:** `src/server/internal/releasecontract/effect_registry.go:269`, `src/server/internal/releasecontract/effect_registry.go:425`, `src/server/internal/releasecontract/effect_registry_test.go:61`, `src/server/cmd/server/main.go:239`, `scripts/verify-readiness-contract.sh:26`

**Issue:** `appendExecutorEffectSurfaces` declares Agent seams present when source text merely contains markers such as `"builtin"` or `CategoryBuiltin`; a dead constant, comment, or unrelated string can satisfy the exact join after the real guard/effect call disappears. `VerifyEffectCoverage` also skips capability-authority verification when `authorities.Valid()` is false. Its runtime test uses a two-row synthetic manifest, while production has a separate permissive `runtimeEffectRegistry` that accepts identical duplicate registrations. No production command or Phase gate invokes `VerifyEffectCoverage`, so the checked-in manifest, static discovery, real production registry, and startup authorities are never joined.

**Fix:** Discover concrete guard-to-effect call chains with Go AST/type information, require valid authorities unconditionally, expose a strict snapshot of the production registry, and add a gate command that joins the checked-in manifest, static discoveries, production descriptors, profile, and authorities. Add mutations that delete or relocate each real guard/effect while leaving marker text behind.

### CR-02 - Strict router composition bypasses Admin model-catalog readiness

**File/line:** `src/server/internal/http/router.go:348`, `src/server/internal/admin/service.go:214`, `src/server/internal/admin/channel_service.go:247`, `src/server/internal/admin/channel_service.go:307`, `src/server/internal/admin/channel_service.go:359`

**Issue:** The production router always falls back to `admin.NewService`, including strict mode, instead of the authority-requiring `admin.NewReadinessService`. Model authorization is conditional on `s.modelReadiness != nil`, so sync, detect, and apply paths can probe and persist model data without the current catalog/Guard authorization required by the phase contract.

**Fix:** Construct `admin.NewReadinessService` with the startup `Guard`, `Authorities`, and `Effects` carrier whenever strict runtime composition creates the service. Make strict construction fail when that carrier is absent, and add a production-composition test proving denied/unknown/stale models produce zero upstream and store mutations.

### CR-03 - Marketplace checkout provider dispatch is unguarded in production

**File/line:** `src/server/internal/http/router.go:381`, `src/server/internal/http/marketplace_handler.go:315`, `src/server/internal/http/marketplace_handler.go:319`

**Issue:** Router composition installs `withMarketplaceCheckout` but omits `withMarketplaceFinancialReadiness`. The handler then calls `h.readiness.require`; the nil receiver is treated as success, so `CreateCheckoutSession` can reach Stripe or another payment provider without current financial readiness. Settlement readiness protects local order creation but does not authorize the later provider dispatch.

**Fix:** Inject the same `marketplace.FinancialReadiness` carrier into the marketplace handler in strict composition, and replace the option-only construction with a strict constructor that rejects a missing readiness carrier. Add a router-level test that denial leaves both checkout-provider and post-order store counters at zero.

### CR-04 - Production Agent web search is injected after authorized tool construction

**File/line:** `src/server/internal/http/server.go:125`, `src/server/internal/http/server.go:142`, `src/server/internal/http/server.go:147`, `src/server/internal/agent/executor.go:132`, `src/server/internal/agent/executor.go:149`, `src/server/internal/mcp/builtin.go:34`

**Issue:** Strict runtime builds `ToolRuntimeOptions` without `WebSearchProvider`, constructs the authorized Agent service, and only then calls `SetWebSearchProvider`. The setter updates one field but does not install the instance-scoped `mcp.NewWebSearchTool` or its capability binding; that happens only when the provider is present during `NewAuthorizedToolExecutor`. The executor therefore retains the cloned legacy global-backed `mcp.BuiltinTools["web_search"]`, which is normally unconfigured and can diverge from the intended per-attempt authorization chain.

**Fix:** Build the provider before the Agent service and include it in `ToolRuntimeOptions.WebSearchProvider`. Alternatively, make the setter atomically install an authorized instance-scoped tool without re-registering descriptors. Add a real production-composition test that executes web search and asserts one construction registration plus current-generation guard/provider counts.

### CR-05 - Relay semantic-cache hits bypass current model readiness

**File/line:** `src/server/internal/relay/router.go:396`, `src/server/internal/relay/router.go:418`, `src/server/internal/relay/router.go:439`

**Issue:** A semantic-cache hit is returned as a successful, usage-recorded AI response before `requireModel` runs. A model that is now blocked, stale, deleted, or disabled can therefore continue returning billable successful responses from cached data.

**Fix:** Resolve and require current model authorization before cache lookup and before any success/usage recording. Keep the provider-effect guard immediately before the actual provider callback. Add a cache-hit test that advances readiness to denied and observes zero cache-return, usage-success, quota, and provider deltas.

### CR-06 - Strict Relay permanently rejects Files API routes

**File/line:** `src/server/internal/relay/router.go:79`, `src/server/internal/relay/router.go:439`, `src/server/internal/relay/handler/files.go:202`, `src/server/internal/relay/handler/files.go:279`

**Issue:** Every billing route now calls model authorization, but Files upload/content/get/delete paths invoke `RouteWithBilling` with an empty model. `routerReadiness.requireModel` rejects an empty model as `capability_unknown`, so these non-model APIs cannot dispatch in strict runtime.

**Fix:** Author and resolve non-model catalog/effect subjects by API class, or limit model resolution to model-bearing APIs while still requiring the correct provider capability for Files. Add strict router tests for upload and passthrough operations that prove authorization and downstream dispatch without inventing a model.

### CR-07 - Canonical Compose and Kubernetes deployments cannot become ready

**File/line:** `src/server/cmd/server/main.go:291`, `src/server/cmd/server/main.go:293`, `deploy/kubernetes/app-deployment.yaml:53`, `scripts/verify-readiness-deployment-harness.sh:201`

**Issue:** When `OBLIVIOUS_READINESS_PROBE_BASE_URL` is absent, startup synthesizes a blocked observation for every dependency. The variable is configured only by the disposable harness; the canonical Kubernetes workload and Compose server do not set it or deploy a compatible probe service. Their `/readyz` therefore remains 503 regardless of the actual configured dependencies.

**Fix:** Build deployment-owned probes from the real DB/Redis/Qdrant/ClickHouse/Kafka/service configuration, or explicitly deploy and configure a supported probe endpoint in every canonical asset. Add a no-harness Compose/Kubernetes contract test that reaches `/readyz` using the shipped topology.

### CR-08 - Admin and App readiness projections advertise stale capabilities as enabled

**File/line:** `src/server/internal/http/readiness_handler.go:132`, `src/server/internal/http/readiness_handler.go:138`, `src/server/internal/http/readiness_handler.go:159`, `src/server/internal/http/readiness_handler.go:166`

**Issue:** Both projections ignore `evaluation.ErrorCode`. When the current generation is stale, the manager returns the last capability values with `readiness_stale`; Admin and App still return HTTP 200 and derive `Enabled: true` from those old values. Clients can continue displaying and attempting stale capabilities even though `/readyz` has failed closed.

**Fix:** Check the evaluation-level error before rendering. Return a sanitized readiness error, or force every item disabled with an explicit top-level stale/unavailable status. Add exact-expiry tests for both endpoints and assert no enabled item survives.

### CR-09 - Batch polling uses one arbitrary provider for every persisted batch

**File/line:** `src/server/internal/http/server.go:301`, `src/server/internal/http/server.go:310`, `src/server/internal/http/server.go:443`, `src/server/internal/relay/store.go:33`, `src/server/internal/relay/batch_polling_worker.go:265`

**Issue:** Runtime constructs one `OpenAIBatchStatusClient` from the first enabled Relay channel. `RelayBatchPollingJob` persists no channel/provider identity, so every batch is later polled with that adapter's base URL and API key. In a multi-provider pool, a batch can be queried against the wrong provider and then retried, dead-lettered, or financially finalized from an invalid result.

**Fix:** Persist the selected channel/provider identity when registering a batch, resolve the matching enabled adapter for each job, and fail closed if that exact provider is unavailable. Add a two-provider integration test with distinct endpoints/keys and verify each job reaches only its originating provider.

## Warnings

### WR-01 - A context-ignoring readiness probe leaks a goroutine per refresh

**File/line:** `src/server/internal/releasecontract/readiness_manager.go:335`, `src/server/internal/releasecontract/readiness_manager.go:342`

**Issue:** Each probe is wrapped in an inner goroutine so the outer refresh can time out. If `Probe.Run` ignores context and never returns, the inner goroutine remains forever; repeated refreshes accumulate leaked work even though callers observe bounded completion.

**Fix:** Require and test context-honoring probe implementations, or run probes through a bounded worker pool that prevents a timed-out dependency from receiving unbounded new work.

### WR-02 - MCP Connect reports connected after failed protocol completion

**File/line:** `src/server/internal/mcp/client.go:223`, `src/server/internal/mcp/client.go:226`, `src/server/internal/mcp/client.go:232`

**Issue:** Failure of `notifications/initialized` is ignored, and `tools/list` failure is explicitly treated as nonfatal before status is persisted as connected. A readiness denial or transport failure between initialize and these steps can therefore produce a successful `Connect` with an unusable connection.

**Fix:** Treat initialized and initial tool discovery as required protocol steps in strict runtime, set error status on failure, and add a denial-between-steps test with no connected-state write.

### WR-03 - Compatibility ToolExecutor remains allow-open

**File/line:** `src/server/internal/agent/executor.go:67`, `src/server/internal/agent/executor.go:223`, `src/server/internal/agent/service.go:97`

**Issue:** `NewToolExecutor` creates `strict=false`, and `authorizeTool` returns success in that state. This contradicts the plan requirement that retained one-argument compatibility construction deny every effect. Production currently intends to inject the authorized executor, but service fallback code still makes the allow-open constructor reachable if wiring regresses.

**Fix:** Make the compatibility value deny before all effects, reserve an explicit test-only helper for permissive unit fixtures, and add an AST plus dynamic production-composition assertion that no runtime path calls the compatibility constructor.

### WR-04 - Strict chat mutation decoding accepts trailing JSON values

**File/line:** `src/server/internal/http/chat_handler.go:130`

**Issue:** `decodeStrictChatMutation` disallows unknown fields but performs only one `Decode`. Bodies containing a valid object followed by another JSON value are accepted, weakening the claimed strict request boundary.

**Fix:** Require a second decode to return `io.EOF` and reject trailing tokens. Add concatenated-object and object-plus-scalar regression cases.

### WR-05 - Concurrent Bootstrap calls can publish generation 2

**File/line:** `src/server/internal/releasecontract/readiness_manager.go:266`, `src/server/internal/releasecontract/readiness_manager.go:304`

**Issue:** The nil-generation check occurs before probe work and outside `publicationMu`. Two concurrent Bootstrap callers can both pass the check; the first publishes generation 1 and the second then publishes generation 2 instead of failing as an already-bootstrapped caller.

**Fix:** Serialize Bootstrap state transition before probing, or add a dedicated atomic bootstrapping state. Extend the race suite to require exactly one successful Bootstrap and generation 1.
