## Core Domain Contracts

### Keep the approved manager interface stable

```go
type ReadinessManager interface {
    Bootstrap(context.Context) error
    StartRefresh(context.Context)
    Require(capabilityID string) error
    Evaluate() Evaluation
    ExportAudit(path string) error
}
```

`Bootstrap` publishes generation 1 after a complete bounded observation/evaluation cycle. A blocked dependency observation is data, not necessarily a bootstrap error; structural inability to produce a coherent generation is an error. `StartRefresh` starts exactly one periodic loop, returns after the loop is owned, and stops that loop with its context. `Require` and `Evaluate` atomically load the current snapshot and pass current clock time through the same evaluator for freshness/identity verdicts; they never read disk or probe synchronously.

### Immutable snapshot and typed verdicts

```go
type Availability string

const (
    AvailabilityEnabled  Availability = "enabled"
    AvailabilityDisabled Availability = "disabled"
    AvailabilityBlocked  Availability = "blocked"
)

type CapabilityEvaluation struct {
    CapabilityID string
    Commitment   string
    Availability Availability
    ReasonCode   string
    Dependencies []string
}

type Evaluation struct {
    Identity     BuildIdentityV1
    Profile      string
    Generation   uint64
    CheckedAt    time.Time
    ValidUntil   time.Time
    Capabilities map[string]CapabilityEvaluation
}

type Snapshot struct {
    Evaluation   Evaluation
    Observations []Observation
}
```

Use Phase 31 exact commitment and identity types when available. The essential rule is that a published `Snapshot` and all nested collections are immutable. Return defensive copies from inspection APIs unless the concrete representation guarantees read-only access.

### One evaluator and an injectable clock

```go
type Clock interface {
    Now() time.Time
}

type Evaluator interface {
    Evaluate(
        contract Contract,
        identity BuildIdentityV1,
        profile Profile,
        generation uint64,
        observations []Observation,
        now time.Time,
    ) (Evaluation, error)
}
```

The evaluator normalizes `now` and observation timestamps to UTC and compares epoch nanoseconds. It derives `ValidUntil` from the oldest applicable observation plus authored max age. Handlers and workers test only the returned verdict/error; they never call `time.Since` or recompute expiration.

### Bounded probe contract

```go
type Observation struct {
    ProbeID       string
    DependencyID  string
    CapabilityIDs []string
    Availability  Availability
    ReasonCode    string
    ObservedAt    time.Time
    Detail        map[string]string
}

type Probe interface {
    ID() string
    Run(context.Context) Observation
}
```

The manager creates a deadline-bound child context for every applicable probe. It derives that set from the selected profile and never constructs/runs probes for excluded capabilities or candidate topology assets. The probe adapter converts dependency timeout/error into one typed blocked observation before returning; a cancellation-ignoring fake proves the manager deadline path can synthesize that observation and return while the test releases the fake goroutine. Manager validation rejects empty IDs, unknown capabilities, unknown states, invalid reason codes and sensitive detail keys as structural errors rather than dependency observations.

## Atomic Publication Pattern

```go
type Manager struct {
    contract  Contract
    identity  BuildIdentityV1
    profile   Profile
    evaluator Evaluator
    probes    []Probe
    clock     Clock
    current   atomic.Pointer[Snapshot]
    refreshMu sync.Mutex
}

func (m *Manager) refresh(ctx context.Context, next uint64) error {
    m.refreshMu.Lock()
    defer m.refreshMu.Unlock()

    observations, err := m.runBoundedProbes(ctx)
    if err != nil {
        return err
    }
    evaluation, err := m.evaluator.Evaluate(
        m.contract, m.identity, m.profile, next, observations, m.clock.Now(),
    )
    if err != nil {
        return err
    }
    candidate := freezeSnapshot(evaluation, observations)
    m.current.Store(candidate)
    return nil
}
```

The code above illustrates ownership, not the final Phase 31 type names. `runBoundedProbes` returns an error only when it cannot construct a structurally complete observation set; ordinary dependency failures are blocked observations. Important properties:

- serialize publications so two refreshes cannot reuse/reorder a generation;
- build the full candidate before `Store`;
- leave `current` byte-for-byte unchanged on any failure;
- derive next generation from current under the publication lock;
- perform audit export after publication without converting the file into authority;
- make `Require` a read-only atomic load plus evaluator-owned current-time verdict mapping, so expiry takes effect without another refresh.

Do not refresh synchronously from `Require`; a slow dependency would move outbound latency and authorization semantics into every effect path.

## Manager-Backed Guard Pattern

Boundary context is useful for telemetry and tests, but must not create another verdict interface:

```go
type Boundary string

const (
    BoundaryHTTP         Boundary = "http_dispatch"
    BoundaryGRPC         Boundary = "grpc_dispatch"
    BoundaryWorkerClaim  Boundary = "worker_claim"
    BoundaryWorkerEffect Boundary = "worker_effect"
    BoundaryOutbound     Boundary = "outbound_dispatch"
    BoundaryFinancial    Boundary = "financial_dispatch"
    BoundaryOperation    Boundary = "operation_dispatch"
)

type Guard interface {
    Require(context.Context, string, Boundary) error
}

type ManagerGuard struct {
    Manager ReadinessManager
    Observe func(context.Context, string, Boundary, error)
}

func (g ManagerGuard) Require(ctx context.Context, capabilityID string, boundary Boundary) error {
    if g.Manager == nil {
        return ErrReadinessUnavailable
    }
    err := g.Manager.Require(capabilityID)
    if g.Observe != nil {
        g.Observe(ctx, capabilityID, boundary, err)
    }
    return err
}
```

All production constructors require a non-nil guard or install a deny-all guard. Tests may inject a spy guard. Never use an allow-all default based on environment.

### Machine-checkable effect inventory

```go
type EffectDescriptor struct {
    ID           string
    CapabilityID string
    Boundary     Boundary
    Owner        string
}

type EffectRegistry interface {
    Register(EffectDescriptor) error
    Snapshot() []EffectDescriptor
}
```

`config/release/readiness-effect-surface.v1.json` is the independently reviewed expected set. Each entry has a stable seam ID, repository-relative owner package/symbol, boundary class, referenced capability ID, typed static-discovery signature and profile applicability/disposition. It is bound through the authored contract `surfaceReferences`, but it cannot define or change capability commitment/profile policy.

Every production guard wiring registers one stable runtime descriptor during side-effect-free construction. A Go source/type discovery pass independently enumerates recognized HTTP/gRPC dispatch, worker claim/effect, outbound, financial and operation calls. The verifier first joins every discovered source seam to exactly one expected manifest disposition. It then projects expected entries through the selected profile and requires runtime descriptors to equal only the applicable set. An excluded candidate remains statically inventoried but has zero route/service/probe/descriptor registration. Missing/extra seams, duplicate IDs, unknown capability IDs, owner/signature mismatch, unknown boundaries and zero applicable rows all fail. Descriptor registration is evidence of wiring, not authorization; the actual effect still calls the manager-backed guard.

Negative fixtures independently remove one expected entry, hide one static discovery, omit one runtime registration, duplicate an ID, substitute an unknown capability and change a boundary class. Each mutation must fail before a release pass. The final join covers HTTP, gRPC, worker claim, worker effect, outbound, financial and effectful operation classes.

## Startup and Lifecycle Pattern

Current `NewServer` starts goroutines. Refactor toward a build result with explicit ownership:

```go
type Runtime struct {
    Server          *http.Server
    StartBackground func(context.Context)
    Close           func(context.Context) error
}

type ServerOptions struct {
    Readiness ReadinessManager
    Guard     Guard
}

func BuildRuntime(cfg config.Config, database *sql.DB, options ServerOptions) (*Runtime, error)
```

`BuildRuntime` constructs stores, services, router and worker values but starts no goroutine and makes no Provider call. `main.go` owns sequence:

```go
contract, identity, profile := loadTrustedReleaseInputs()
database := openAndPingDatabase()
applyAndValidateMigrations(database)
manager := buildReadinessManager(contract, identity, profile, database)
must(manager.Bootstrap(rootCtx))
runtime := mustBuildRuntime(cfg, database, manager)
listener := mustOpenListener(runtime.Server.Addr)
go serve(runtime.Server, listener, serverErrors)
manager.StartRefresh(rootCtx)
runtime.StartBackground(rootCtx)
```

Real implementation should return errors instead of the illustrative `must*` helpers. Opening `net.Listener` synchronously proves the control plane can bind before workers start. Shutdown cancels the shared root context, stops accepting new requests, waits for existing server shutdown semantics and closes resources once.

### Standalone services and operation tools

Phase 31 profile policy rejects excluded standalone service entrypoints before they construct DB, listeners, workers or outbound clients. A committed effectful operation tool resolves trusted contract/build/profile inputs, obtains the current manager-backed verdict, and guards immediately before the effect. Contract validation, DB open/ping and migration bootstrap are prerequisites in the authored startup sequence rather than post-bootstrap capability effects, so they retain their explicit fatal rules instead of creating a circular readiness dependency.

The read-only readiness inspector uses the shared Go evaluator against trusted runtime/API state and may emit a typed report. An offline evidence mode may read a runtime-produced audit snapshot for schema/identity/freshness validation, but there is no audit-file authorization reader; supplying an existing JSON path cannot turn it into an enabled verdict or seed a manager.

## HTTP and gRPC Patterns

### Capability-bound HTTP wrapper

```go
func requireCapability(guard Guard, capabilityID string, next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        if err := guard.Require(r.Context(), capabilityID, BoundaryHTTP); err != nil {
            writeReadinessError(w, err)
            return
        }
        next.ServeHTTP(w, r)
    })
}
```

Excluded routes are removed during registration from immutable contract policy, so this wrapper never turns an excluded route into a visible disabled route. Tests wrap a handler that increments a counter and assert zero on disabled/blocked/stale/unknown/unavailable cases.

### gRPC interceptor

Map fully-qualified service/method to a server-owned capability registry and guard before the generated handler. Missing method mapping fails closed with a stable error detail. Streaming RPCs guard initial dispatch and must guard each later Provider/tool/financial effect inside the service; the interceptor alone cannot authorize the lifetime of a stream.

### Health endpoints

```go
func livez(w http.ResponseWriter, r *http.Request) {
    writeJSON(w, http.StatusOK, processLiveness())
}

func readyz(manager ReadinessManager) http.HandlerFunc {
    return func(w http.ResponseWriter, r *http.Request) {
        evaluation := manager.Evaluate()
        writeReadinessEvaluation(w, evaluation)
    }
}
```

`/livez` does not call `Require`, DB, providers or audit file I/O. `/readyz` uses current manager evaluation and returns sanitized summary/reason codes. It fails when a capability that the selected profile requires enabled is blocked or cannot be evaluated; an intentionally disabled conditional capability remains unavailable to its caller without automatically failing process readiness. Neither endpoint returns raw probe detail.

## Worker Claim/Effect Patterns

### Generic two-stage worker

```go
func (w *Worker) runOnce(ctx context.Context) {
    if err := w.guard.Require(ctx, w.claimCapability, BoundaryWorkerClaim); err != nil {
        w.reportDenied(err)
        return
    }
    jobs, err := w.claim(ctx)
    if err != nil {
        w.reportError(err)
        return
    }
    for _, job := range jobs {
        if err := w.guard.Require(ctx, w.effectCapability(job), BoundaryWorkerEffect); err != nil {
            w.releaseOrRetrySafely(ctx, job, err)
            continue
        }
        w.executeEffect(ctx, job)
    }
}
```

`releaseOrRetrySafely` may only perform the existing idempotent bookkeeping needed to avoid a permanently locked claim. It must not call Provider/tool/channel/object/finance dependencies. This exception is explicit and tested; it is not a general permission for local DB mutations.

### Concrete seam checklist

- Schedule: guard before `ClaimDueScheduledTaskRuns`, then before `startClaimedWorkflow`, `RunExecutionUntilBlocked` and agent execution as their capability boundaries require.
- Channel retry: guard before `ClaimDueRetryMessages`, then immediately before each `Service.Send` transport.
- Relay batch: guard before `ClaimBatchPollingJobs`, `RetrieveBatch`, completion/failure finalizers and irreversible terminal state transition.
- Archive: split/inject the archive operation so sink write and source-state mutation each have current authorization.

Keep claim and effect capability IDs explicit in constructors. Do not derive them from Go type names or route paths.

## Outbound and Finance Wrapper Patterns

Wrap the narrow interface that immediately precedes the external call:

```go
type GuardedBatchClient struct {
    Guard        Guard
    CapabilityID string
    Next         BatchStatusClient
}

func (c GuardedBatchClient) RetrieveBatch(ctx context.Context, job RelayBatchPollingJob) (BatchStatusResult, error) {
    if err := c.Guard.Require(ctx, c.CapabilityID, BoundaryOutbound); err != nil {
        return BatchStatusResult{}, err
    }
    return c.Next.RetrieveBatch(ctx, job)
}
```

The fixed-ID wrapper above is valid for a static seam whose capability mapping is server-owned and independent of request/persisted catalog choice, such as one batch-status operation, Provider transport class or external channel adapter. Dynamic model and tool subjects must not cache or accept a capability ID. Their wrapper constructs the current `CatalogSubject` from trusted runtime/persisted data and calls `CatalogAuthorizer.ResolveAndRequire` in the same call immediately before `Next` dispatch.

If Relay or Chat can fallback across models, every model attempt constructs its own subject, resolves against the current contract and guards the current manager generation; the Provider transport separately uses its server-owned effect mapping. MCP, web search and builtin/custom tools follow the dynamic catalog pattern. External channels use server-owned static effect mappings, not an invented channel catalog binding. A capability returned earlier in a response or stored row is diagnostic data only.

For finance, guard before both external provider creation/dispatch and any local transition that asserts a new dispatch has occurred. Tests inject creators/clients that count calls and stores that record writes, then assert denial leaves both at zero except explicitly safe idempotency lookup/denial audit. A verified provider webhook for an effect already dispatched before expiry may apply idempotent reconciliation; tests prove that path updates existing lifecycle state without calling a provider or initiating another refund/payout/settlement.

## Catalog Resolver Pattern

```go
type CatalogSubject struct {
    Kind    string
    ID      string
    Runtime string
}

type CapabilityID string

type CatalogResolver interface {
    Resolve(CatalogSubject) (CapabilityID, error)
}

type CatalogAuthorizer struct {
    Resolver CatalogResolver
    Guard    Guard
}

func (a CatalogAuthorizer) ResolveAndRequire(
    ctx context.Context,
    subject CatalogSubject,
    boundary Boundary,
) (CapabilityID, error) {
    capabilityID, err := a.Resolver.Resolve(subject)
    if err != nil {
        return "", err
    }
    if err := a.Guard.Require(ctx, string(capabilityID), boundary); err != nil {
        return "", err
    }
    return capabilityID, nil
}
```

DTO rules:

- response DTO exposes `CapabilityID string` as read-only JSON `capabilityId`, populated by the server;
- request DTO has no capability field and strict request decoding rejects `capabilityId`;
- persistence stores model/tool business subject, not an authorization verdict;
- mutation resolves + requires before save;
- execution loads current subject, resolves + requires immediately before dispatch;
- cache key includes contract digest and invalidates on contract change, while execution still guards current generation.

## Admin and App Projection Pattern

Do not reuse one DTO with conditional JSON omission. Define separate types so sensitive fields cannot appear accidentally:

```go
type AdminCapabilityReadiness struct {
    CapabilityID string
    Commitment   string
    Availability Availability
    ReasonCode   string
    Dependencies []string
    Remediation  string
}

type AppCapabilityAvailability struct {
    CapabilityID string
    Availability Availability
}
```

The Admin envelope includes identity, profile, generation, checkedAt, validUntil and full inventory. The app envelope includes only safe enabled/disabled choices needed by selectors/navigation. Excluded capabilities are absent from the app response. Both are derived from the same in-memory evaluation.

## Snapshot Export and Report Adapter Pattern

`ReadinessManager.ExportAudit` serializes strict `ReadinessSnapshotV1`: schema version, trusted identity, selected profile, generation, checkedAt, validUntil, sanitized observations and capability evaluations. It delegates persistence to a shared atomic-file primitive: create parent, deterministic encode, same-directory temp, flush/sync, close, atomic replace, parent sync where supported and temp cleanup on failure.

A separate Go inspector validates an online evaluation or offline runtime-produced snapshot with the same evaluator, then adapts it to Phase 31 `SurfaceReportV1`. Phase 31.1 owns the readiness details registration in `surfacereport`: required `generation`, `checkedAt`, `validUntil`, with no arbitrary keys. The inspector uses the shared report validator/writer; Phase 31.2 invokes/aggregates this producer and never recalculates freshness in Python.

The disposable deployment harness owns a separate deployment details registration and producer. Its report binds explicit monolith profile, canonical workload/probe/audit wiring and harness outcome to the same trusted identity. Readiness and deployment reports have different `surfaceIdentity` values and schemas; neither may stand in for the other.

Rules:

- no read method on the runtime manager audit dependency; only the offline evidence inspector accepts snapshot input;
- no startup fallback to an existing path;
- write errors preserve in-memory snapshot and surface `report_output_unwritable` to evidence/operations;
- public views never return filesystem path, raw probe payload or secret-bearing error text.

## Deployment Patterns

### Container and Compose

- Copy the canonical contract into the runtime image and include the readiness inspection binary built with the same identity flags.
- Use a fixed runtime audit location such as `/var/lib/oblivious/readiness/readiness.json`; create/chown its parent for the non-root runtime user.
- Set `OBLIVIOUS_DEPLOYMENT_PROFILE=monolith` explicitly in Compose.
- Mount a named disposable volume at `/var/lib/oblivious/readiness`; do not mount a file at the final JSON path.
- Docker `HEALTHCHECK` keeps service-readiness semantics through `/readyz`; harness/Kubernetes process-liveness checks use `/livez` separately.

### Canonical Kubernetes workload

`app-deployment.yaml` must contain:

- explicit monolith profile environment/config input;
- `emptyDir` mounted at `/var/lib/oblivious/readiness`;
- startup and liveness probes on `/livez`;
- readiness probe on `/readyz`;
- no ConfigMap/Secret/file input that supplies readiness verdicts.

The deployment verifier should assert exactly one canonical `oblivious-server` Deployment source. If `server.yaml` is retained, a deterministic generator/check proves it matches the canonical source and labels it compatibility-only.

### Disposable harness

Follow existing `mktemp` + `trap` cleanup patterns. Use a unique Compose project name, isolated volume names and runtime-generated audit output. The harness sequence is build -> DB healthy -> migration complete -> server live -> server ready -> audit/identity assertions -> forced blocked/stale negative cases -> cleanup.

Environment preflight failures exit nonzero with stable diagnostics. A summary JSON records the failure and `skippedChecks: []`; it never changes an unavailable committed check into a skip.

## Testing Patterns

### Clock boundary table

```go
tests := []struct {
    name    string
    now     time.Time
    wantErr string
}{
    {name: "valid at exact max-age boundary", now: observedAt.Add(maxAge)},
    {name: "stale one nanosecond later", now: observedAt.Add(maxAge).Add(time.Nanosecond), wantErr: "readiness_stale"},
    {name: "future at exact skew boundary", now: observedAt.Add(-futureSkew)},
    {name: "future one nanosecond beyond", now: observedAt.Add(-futureSkew).Add(-time.Nanosecond), wantErr: "readiness_unavailable"},
}
```

Use authored durations loaded through the contract fixture; do not hard-code a second set in the evaluator test package.

### Zero-call denial

Each boundary test includes a fake dependency whose call increments an atomic counter or fails the test. Run the same table for disabled, blocked, unknown, unavailable, stale, identity mismatch and nil manager. Assert response/error class plus zero claim/effect/provider/tool/channel/finance calls.

### Refresh retention

Publish a valid generation, advance fake clock, force a structural coordinator/evaluator failure that prevents a coherent candidate, run refresh, and assert pointer generation/checkedAt/validUntil are unchanged. A separate case makes a dependency probe timeout/error and asserts publication of a new blocked generation. Advance beyond the retained generation's original validity and assert `Require` denies. This is the core proof that structural refresh failure cannot keep a capability alive while ordinary dependency failure denies immediately.

### Race proof

Run concurrent `Require`/`Evaluate` readers while controlled refreshes publish generations, then execute the package with `go test -race`. Assert readers observe complete generations only and generation never decreases.

## Anti-Patterns

- Reading audit JSON in startup, a guard, `/readyz`, Admin route or inspection CLI authorization path.
- Reimplementing max-age/future-skew comparisons in Python, shell, handlers or workers.
- Guarding only HTTP ingress, only worker loop entry or only the first provider attempt.
- Pinning a generation for a multi-step workflow and using it to authorize later effects.
- Starting worker/health goroutines from a constructor before listener bind succeeds.
- Treating a missing manager as allow, even in development or tests.
- Accepting or persisting caller-supplied capability IDs.
- Serving Admin and app projections from the same broad DTO.
- Maintaining two hand-authored Kubernetes Deployments for the same workload.
- Converting Docker/DB absence into a successful fixture-only completion result.
- Calling E2 harness output target readiness, profile parity or commercial release proof.

## Planner Guardrails

1. Stabilize evaluator/manager/guard contracts before parallel consumer plans.
2. Keep each plan at two or three tasks and no more than nine touched files; split worker/outbound families when ownership would exceed that bound.
3. Give every side-effect family a named capability mapping and zero-call denial test.
4. Keep `app-deployment.yaml` canonical and prove the treatment of `server.yaml` automatically.
5. Run narrow implementation/verification tests through Phase 31 `scripts/run-go-tests-matched.sh`, related package tests and `git diff --check`; raw targeted `go test -run` is not evidence because zero matches succeed.
6. For identity-bearing work, run Stage A in a temporary clean Git fixture, create the atomic commit, then run Stage B against that exact clean `HEAD`; do not push until Stage B passes, and rerun it after any follow-up commit.
7. Record repository-local evidence class, environment, exact commit, migration state, skips and residual risk in every completion report.
