**Gathered:** 2026-07-16

<domain>
## Phase Boundary

本阶段把 Phase 31 交付的 authored release contract、显式 deployment profile、可信 `BuildIdentityV1` 和统一报告协议接入当前 monolith runtime。完成后，当前进程必须由一个内存中的 `ReadinessManager` 持续计算 capability availability，并在每一次新的 HTTP/gRPC dispatch、worker claim、不可逆 worker effect、Provider/model/tool/channel 调用和财务 dispatch 前 fail closed。

本阶段完成 `RELS-01`，但不提前完成 `RELS-02`。OpenAPI/frontend/protobuf/migration 的全表面双向漂移、统一 aggregate owner 和 CI 聚合属于 Phase 31.2。身份、租户、durable execution、Relay 业务主链、真实客户旅程、财务闭环、持久观测、部署模式 parity、供应链和 target release 仍分别属于 Phase 32-39。

本阶段只形成 repository-local E1/E2 证据。任何本地 fixture、容器 harness、审计 JSON、页面或健康端点都不能被描述为 E3 target evidence、E4 same-commit release、商业发布完成或非 monolith profile parity。

</domain>

<decisions>
## Implementation Decisions

### 权威、时间与快照

- **D-RDY-01:** 单一运行授权源：`ReadinessManager` 是 runtime 唯一 capability 授权源。磁盘上的 readiness JSON 只允许由当前 manager 写出作为审计证据；startup、route、worker、outbound、finance、CLI 或其他进程不得读取该文件决定是否授权。
- **D-RDY-02:** 单一 evaluator：一个 Go evaluator 统一处理 trusted build identity、显式 profile、snapshot generation、observation availability、freshness、future skew、capability verdict 和稳定 reason code。HTTP handler、worker、shell、Python 和 frontend 不得复制时间或 verdict 逻辑。
- **D-RDY-03:** 固定 authored 时间合同：monolith 的 refresh interval 为 `30s`、max age 为 `120s`、allowed future skew 为 `30s`。三者来自 Phase 31 authored profile，不能由 request、旧审计文件或运行时 fallback 覆盖。
- **D-RDY-04:** 精确 freshness：时间比较使用 UTC epoch nanoseconds。`validUntil` 由最老适用 observation 的时间加 max age 推导；边界相等仍有效，超过一纳秒即为 `readiness_stale`。未来 observation 超过 allowed future skew 必须拒绝。
- **D-RDY-05:** 单调 generation：成功 bootstrap 发布 generation 1；每次完整、可评估的 refresh 才原子发布下一 generation。refresh 失败可以保留上一 generation，但不得修改其 `checkedAt`、observation 时间或 `validUntil`，因此旧状态会自然过期。
- **D-RDY-06:** 不可变读路径：reader 只看到一个完整、不可变的 snapshot。probe、evaluation、audit serialization 先在 publication 外构造；禁止就地修改已发布 map/slice，也禁止让部分 probe 结果覆盖当前 generation。

### 启动与降级语义

- **D-RDY-07:** 固定启动序列：`contract/profile/build validation -> DB open/ping -> migration apply/ledger validation -> bounded bootstrap probes -> generation 1 -> listener/control plane -> workers/periodic refresh`。显式 profile 或 trusted identity 缺失时必须在 DB 前失败。
- **D-RDY-08:** fatal 边界：DB open/ping 或 migration apply/ledger validation 失败仍为进程 fatal，不能启动 listener。其他适用 dependency probe 失败时发布带 `blocked` observation 的 generation 1；进程可以提供 `/livez` 和授权的 operator inspection，但 `/readyz`、release gate 和对应的新 side effect 必须失败。
- **D-RDY-09:** bounded bootstrap：每个适用 dependency probe 都必须接受 context deadline，bootstrap 不允许无限等待。dependency timeout/error 在 deadline 内合成 typed `blocked` observation 并参与下一 generation；缺失/畸形 observation 或未知 reason code 是结构性 evaluation failure，不能被默认为 enabled。`excluded` capability/profile 不注册也不 probe；候选资产存在不能触发探测或外部调用。
- **D-RDY-10:** 构造不启动后台副作用：当前 `NewServer` 构造期内启动 Relay health checks 和 worker 的行为必须拆开。server/router 可以在 bootstrap 后构造，但 worker 和周期 refresh 只能在 listener/control plane 建立后显式启动，并与 shutdown context 绑定。

### 持续 guard 与在途工作

- **D-RDY-11:** 同一 guard 与独立 coverage authority：manager 通过一个窄的 guard adapter 注入 HTTP router、gRPC adapter、worker、Relay/Chat、MCP/tool、channel、finance 和 effectful operation tool。adapter 只能增加 boundary/telemetry context，最终 verdict 必须来自同一 manager generation。`config/release/readiness-effect-surface.v1.json` 是 effect seam coverage 的独立 expected inventory，只引用 Phase 31 capability ID，不拥有 commitment/profile 真相；它 disposition 全部静态发现 seam，并声明 profile applicability。verifier 先对 expected inventory 与 Go 静态发现做全量 join，再要求 server-owned runtime descriptors 精确等于 selected profile 的 applicable projection；excluded seam 必须被 inventory 解释但保持零 runtime registration。missing、extra、duplicate、unknown capability 或未分类 boundary 一律失败。excluded standalone service entrypoint 由 Phase 31 profile policy 在构造依赖前拒绝；read-only readiness inspector 不能把审计 JSON 变成授权。
- **D-RDY-12:** ingress guard：每次新的 HTTP 或 gRPC dispatch 都在业务 handler/service 前重新调用 guard。`excluded` surface 不注册并表现为 `404`；`disabled` 返回稳定 `capability_disabled`；`blocked` 返回 `503` 和 `capability_blocked`；unknown、unavailable、stale 和 identity mismatch 一律拒绝且不得调用业务依赖。
- **D-RDY-13:** worker 双 guard：worker 在 claim 前 guard 一次，并在每个 job 的不可逆 effect 前再次 guard。claim 后 readiness 失效时可以按现有幂等/取消语义记录安全的释放、失败或重试状态，但不得发起 Provider、tool、channel、对象写入、workflow/agent execution、结算或其他新 effect。
- **D-RDY-14:** outbound guard：每次 Provider、model、builtin/custom/MCP tool、web search 和外部 channel dispatch 前重新 guard。上层 ingress 已通过不能代替 dispatch 点检查；retry、fallback 和 batch retrieval 都视为新的 dispatch。
- **D-RDY-15:** finance guard：checkout、refund、payout、settlement 和任何外部 payment provider dispatch 前重新 guard。denial 必须由 zero-call spy 证明不会创建外部请求，也不会提前写入会把操作伪装成已发出的不可逆状态。已经发生 provider effect 的签名 webhook/reconciliation 可按 `D-RDY-16` 幂等完成账本收尾，但不得借此发起新的 refund、payout 或 settlement effect。
- **D-RDY-16:** 在途边界：snapshot 失效前已经开始的工作可以按当前 idempotency/cancellation 语义完成安全收尾；这不是 generation pinning，也不授权后续步骤。一个多步执行在每个新 effect 前都必须重新读取当前 manager。

### 视图、健康与审计

- **D-RDY-17:** Admin 与 app 分离：Admin full inventory 显示 committed、conditional、excluded capability、dependencies、reason code、generation、时间、identity、修复提示和证据引用。authenticated app-safe projection 只返回当前用户界面需要的非敏感 committed/conditional 项，不泄露 secrets、credential、内部地址、原始 probe payload 或 excluded inventory。
- **D-RDY-18:** health 语义：`/livez` 只证明进程和 control plane 存活，不读取审计文件，也不把 dependency readiness 伪装为 liveness。`/readyz` 直接消费 manager 当前 evaluation；当前 profile 要求 enabled 的 capability 一旦 blocked、unknown、unavailable 或 stale，就返回非成功结果和稳定、脱敏的 reason codes。按 authored policy 有意 disabled 的 conditional capability 仍拒绝自身 dispatch，但不单独把整个进程判为 unready。
- **D-RDY-19:** snapshot export 与 report adapter：每次成功 publication 尝试原子输出 typed `ReadinessSnapshotV1` 审计文件。写出失败必须产生 `report_output_unwritable` 并使 repository release evidence 失败，但不得回读旧文件、延长有效期或替换内存授权源。Phase 31.1 同时拥有 Go inspector 和 shared `SurfaceReportV1` 的 `readiness` details registration（`generation`、`checkedAt`、`validUntil`）；inspector 可离线读取 runtime-produced snapshot 做 schema/identity/freshness 验证并生成 surface ID 为 `readiness` 的 report，但该结果永不授权 runtime。operator HTTP view 直接读取 manager。

### Catalog capability authority

- **D-RDY-20:** 服务端绑定：Phase 31 contract 的 `catalogBindings` 是 model、builtin tool 和严格 custom/MCP runtime class 到 capability ID 的唯一权威。response DTO 可以返回只读 `capabilityId`；create/update request 不能接受 caller-supplied capability ID。
- **D-RDY-21:** 双重重解析：mutation 在保存 model/tool/routing target 前按服务端 catalog 解析并授权；execution 在真正 dispatch 前再次按当前 catalog、当前 persisted subject 和当前 generation 解析并授权。旧数据中的 capability 字段、frontend selector 或缓存结果都不可信。
- **D-RDY-22:** 未知绑定 fail closed：未绑定、歧义、runtime class 不匹配或已删除的 model/tool subject 返回 `capability_unknown` 或更具体的 authored reason code，且 execution zero-call。UI 隐藏/禁用只是 app-safe projection 的呈现，不是最终安全边界。

### Packaging、canonical deployment 与 harness

- **D-RDY-23:** 制品自包含：`Dockerfile.server` 必须打包 release contract、readiness inspection CLI 和可写 audit path，并继承 Phase 31 的 binary/OCI/contract identity 校验。镜像、Compose 和 Kubernetes 都不挂载任何 readiness 输入文件。
- **D-RDY-24:** 显式 monolith profile：Docker Compose 的 `oblivious-server` 和 Kubernetes workload 都显式提供 `monolith`，并为 audit export 提供独立可写存储。缺失 profile 不能由 contract 的 `defaultProfile` 或 asset 名称补齐。
- **D-RDY-25:** 单一 Kubernetes 权威：`deploy/kubernetes/app-deployment.yaml` 是 canonical workload。它必须使用 `/livez` 作为 startup/liveness、`/readyz` 作为 readiness，并挂载 audit `emptyDir`。`deploy/kubernetes/server.yaml` 只能变成由 canonical workload 生成的兼容产物或从 release validation inventory 移除，不能继续作为第二份手写权威。
- **D-RDY-26:** disposable harness：repository-local harness 构建镜像、应用真实 migration、启动 monolith、等待 live/ready、读取 runtime audit、核对 binary/OCI/contract identity，并在成功或失败后清理临时 Compose project、container 和 volume。Phase 31.1 在 shared registry 中拥有 `deployment` details schema，并由该 harness 产出 surface ID 为 `deployment` 的独立 `SurfaceReportV1`；它不能与 `readiness` report 折叠。Docker daemon 或可用 DB 缺失是明确失败，不是 skip 或通过。

### 证据和声明边界

- **D-RDY-27:** 完成证据：Phase 31.1 的通过结论必须记录 evidence class、环境、命令、build/contract/profile identity、migration state、pass/fail、skips 和 residual risk。committed check 的任何非空 skip 都失败。identity-bearing slice 继承 D-FND-11：开发期只在临时 clean Git fixture 做 Stage A，原子 commit 后对 exact clean `HEAD` 做 Stage B，Stage B 通过前不得 push。
- **D-RDY-28:** 声明上限：Phase 31.1 最多证明 E1 单元/fixture 和 E2 repository runtime/container 行为。它不证明 live Provider/payment/storage、target Kubernetes、profile parity、签名/provenance、真实客户 lifecycle 或最终 no-skip 商业发布。

### Planner Discretion

- `src/server/internal/releasecontract/` 内 evaluator、manager、probe 和 catalog resolver 的具体文件拆分可按职责调整，但不得产生第二个 verdict 或时间实现。snapshot export 复用 Phase 31 atomic-file primitive 或严格等价的 shared primitive；inspector report 必须使用 Phase 31 `surfacereport` validator/writer，并只注册本阶段固定的 readiness details。
- probe 的组合、并发上限、deadline 分配和 reason-code-to-remediation 文案可由 planner 依据 authored contract 和现有依赖客户端确定；不得放宽 `30s / 120s / 30s` 时间合同。
- `server.go` 可通过 runtime builder、lifecycle controller 或等价显式 start 方法移出构造期 goroutine；必须保留锁定启动顺序和 shutdown ownership。
- `server.yaml` 选择 generated compatibility 或退出 validation inventory 均可；无论选择哪种，都必须有自动化测试证明只有 `app-deployment.yaml` 是 canonical source。

</decisions>

## Existing Code Insights

### Reusable Assets

- `migrations.Apply` and the current production readiness ledger check already define DB/migration fatal semantics; reuse them rather than building a second migration truth。
- `RouterOptions` already carries explicit runtime dependencies into route wiring and is the natural injection seam for the readiness guard and projections。
- Worker constructors already accept config and interfaces, making guard/clock/zero-call spies testable without global state。
- HTTP handlers already use stable error envelopes through `writeError`; readiness denial should extend that contract instead of inventing another response format。
- Release evidence writers and fixture scripts already demonstrate deterministic JSON, temp-directory cleanup and nonzero failure assertions。

### Current Gaps That Planning Must Close

- `NewServer` currently starts goroutines before `ListenAndServe`, so the authored startup order cannot be achieved by adding one call in `main.go` alone。
- `/readyz` currently checks only DB and production migration ledger; it is not a capability readiness verdict。Kubernetes references `/livez`, but runtime does not register it。
- Worker claim and outbound/financial seams have no shared ongoing readiness guard。
- Docker image、Compose and Kubernetes do not yet package explicit release profile + writable audit output as one contract。
- `app-deployment.yaml` and `server.yaml` are two hand-authored Deployments with the same name, while `k8s-validate.sh` proves only the former is canonical in actual deployment validation。

</code_context>

- Full HTTP/OpenAPI/frontend/protobuf/migration surface parity and aggregate gate ownership remain Phase 31.2。
- Tenant propagation and shared outbound target security policy remain Phase 32; Phase 31.1 only injects capability readiness at the outbound boundary。

- Provider/Chat evidence, customer journeys, financial reconciliation, observability/recovery and deployment parity remain Phase 34-38。
