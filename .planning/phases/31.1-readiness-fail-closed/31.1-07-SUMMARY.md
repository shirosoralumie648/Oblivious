# Phase 31.1 Plan 07: Financial Readiness Guards Summary

**Checkout, Admin refund, Marketplace payout, and settlement dispatch now use startup-bound financial capabilities with per-attempt current readiness checks, while signed lifecycle events remain reconciliation-only.**

## Accomplishments

- Added constructor-scoped billing and Admin financial readiness carriers that resolve `EffectBillingCheckout` and `EffectAdminRefund` only through `RuntimeAuthorities`, register stable `BoundaryFinancial` descriptors once, and guard before local mutations and immediately before checkout provider calls.
- Added `WithMarketplaceFinancialReadiness` plus a fail-closed constructor to `SettlementService`; order/payout intent creation and every queued or new `CreatePayout` attempt re-read the shared guard. Readiness denial preserves queued state and does not write provider dispatch evidence.
- Renamed the lifecycle dependency boundary to `MarketplaceReconciliationApplier`, retaining a compatibility adapter for existing signed webhook wiring. Reconciliation verbs only apply already-observed local state and cannot expose checkout/refund/payout dispatch methods.

## Decisions Made

- Plan 31.1-02 remains the sole startup composition owner; this plan provides explicit readiness-aware constructors/options without adding a second contract/profile reader or global authority.
- A readiness denial after a local intent is intentionally distinct from provider failure: pending/queued identity remains retryable, but no session/provider ID or sent/paid marker is written.
- Existing `MarketplaceSettlementApplier` callers are adapted rather than broken; new code uses the narrower reconciliation verbs.
