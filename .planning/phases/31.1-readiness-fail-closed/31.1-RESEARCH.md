## User Constraints (from CONTEXT.md and approved design)

### Locked Decisions

1. `ReadinessManager` is the sole runtime authorization source; runtime treats JSON snapshots as write-only audit output, while the offline Go inspector may read them only to produce evidence.
2. Authored timing is exactly refresh `30s`, max age `120s`, future skew `30s`; one Go evaluator owns all freshness and verdict rules.
3. Startup order is contract/profile/build validation, DB, migration, bounded probes, generation 1, listener/control plane, then workers/refresh.
4. DB or migration failure is fatal. Other dependency failure publishes `blocked` so liveness/operator inspection can remain available while readiness and new effects fail.
5. Every new HTTP/gRPC dispatch, worker claim, irreversible worker effect, Provider/model/tool/channel call, financial dispatch and effectful operation tool rechecks the current generation; excluded standalone entrypoints fail before dependency construction.
6. Existing in-flight work may finish only within current idempotency/cancellation semantics; it receives no permission to begin another effect after expiry.
7. Admin full inventory and app-safe projection are distinct contracts.
8. `catalogBindings` are server-authoritative. Requests cannot supply capability IDs, and mutation plus execution both re-resolve current bindings.
9. `app-deployment.yaml` is the canonical Kubernetes workload; Compose/Kubernetes package explicit monolith profile and writable audit storage without an authorization snapshot input.
10. Disposable harness failure caused by unavailable Docker or DB is a committed failure, not a skip.
11. Evidence ceiling is repository-local E1/E2. Phase 31.1 cannot make Phase 31.2 or Phase 32-39 claims.

## Summary

Oblivious already has production-oriented DB/migration startup, health endpoints, Relay health checks, four monolith background worker families, several outbound Provider/tool/channel clients and multiple financial entrypoints. The gap is not a missing health endpoint. The gap is that these paths do not share a fresh, identity-bound authorization decision and many background effects start from inside `NewServer` before the listener is established.

The least disruptive architecture is a package-level readiness manager built on Phase 31 immutable contract/policy and `BuildIdentityV1`, plus a narrow guard injected through existing constructors. The manager publishes immutable generations through an atomic pointer, writes audit snapshots only after publication, and exposes projections directly from memory. Startup must be split into build and start phases so bootstrap precedes listener, while worker loops and periodic refresh begin afterward.

The highest-risk work is guard completeness, not evaluator syntax. A guard only at route ingress leaves retries, scheduled jobs, Relay fallback, MCP calls and finance dispatch able to continue after expiry. Validation therefore needs zero-call spies at every effect family, clock-controlled nanosecond boundary tests, and an inventory assertion that maps every runtime effect seam to a capability and guard.

## Live Runtime Inventory

### Startup and constructor ownership

`src/server/cmd/server/main.go` currently executes `config.Load`, `db.Open`, `migrations.Apply`, `NewServer`, then `ListenAndServe`. It does not explicitly ping DB before migration and has no release contract/profile/build/readiness bootstrap step. DB and migration errors are already fatal, which is compatible with the approved design. [VERIFIED: `src/server/cmd/server/main.go`]

`src/server/internal/http/server.go` is not a pure constructor. It loads Relay state, may create fallback model paths, starts Relay health checks, constructs the router, and starts schedule, Relay batch, channel retry and archive goroutines before returning the `http.Server`. This prevents the required listener-before-workers ordering unless construction and lifecycle start are separated. [VERIFIED: `src/server/internal/http/server.go`]

`RouterOptions` already carries stores/services into `NewRouterWithOptions`, so readiness manager, guard, full inventory source and app-safe projection can be injected without package globals. [VERIFIED: `src/server/internal/http/router.go`, `src/server/internal/http/server.go`]

| Worker family | Claim seam | Effect seam | Required checks |
|---|---|---|---|
| Scheduled task | `schedule.Service.RunDueTasks` -> `ClaimDueScheduledTaskRuns` | workflow start/run and agent run in `runClaimed*` | guard before claim and again before workflow/agent execution |
| Channel retry | `channel.Service.ProcessDueRetryMessages` -> `ClaimDueRetryMessages` | `Service.Send`, retry state and channel-health updates | guard before claim and before each external send; denial records safe retry/release state only |
| Relay batch polling | `BatchPollingWorker.runOnce` -> `ClaimBatchPollingJobs` | `RetrieveBatch`, completion/failure finalizers and terminal state writes | guard before claim, provider retrieval and each irreversible finalizer |

The current worker interfaces are narrow enough for injected guard and fake clock tests. Avoid a global manager lookup: workers should receive a capability-bound guard in their constructor so missing wiring fails construction or denies by default. ### Outbound and financial effect seams

| Effect family | Current seam | Readiness concern |
|---|---|---|
| Relay Provider/model | `src/server/internal/relay/router.go` | routing attempt, fallback attempt and provider retry are distinct dispatches; quota/usage cleanup must remain safe on denial |
| Chat Relay transport | `src/server/internal/chat/relay_gateway.go` | ingress readiness cannot authorize a later HTTP call or local fallback |
| MCP/custom tool | `src/server/internal/mcp/client.go` and agent runtime/tool runners | resolve subject + guard immediately before JSON-RPC/tool execution |
| Web search/builtin tool | `src/server/internal/agent/tools/` and configured providers | each tool invocation re-resolves binding and guards; UI metadata is insufficient |
| External channel | `src/server/internal/channel/webhook_adapter.go` and channel service | initial/retry send use a server-owned static effect mapping immediately before transport; channel is not a `catalogBindings` subject |
| Subscription checkout | `src/server/internal/http/billing_handler.go` | select provider only after guard; denial must make provider creator call count zero |
| Marketplace paid checkout | `src/server/internal/http/marketplace_handler.go` plus settlement service | do not create an externally-dispatched state before guard succeeds |
| Refund/settlement/payout | Stripe lifecycle, marketplace settlement and Admin finance paths | guard every newly initiated external/financial transition; already-dispatched signed provider events may reconcile idempotently but cannot initiate another effect |

A single generic middleware cannot cover this table. Reusable wrappers should live close to each outbound interface, while all wrappers delegate the verdict to the same manager-backed guard.

### Health and inspection

`/healthz` is shallow process health. `/readyz` currently checks DB and, in production, the migration ledger. It has no capability generation, freshness, profile or dependency view. Kubernetes already calls `/livez`, but no runtime route is registered. [VERIFIED: `src/server/internal/http/router.go`, `deploy/kubernetes/app-deployment.yaml`]

The new control plane needs three distinct surfaces:

- `/livez`: process/control-plane liveness only;
- `/readyz`: current manager evaluation, suitable for orchestrator readiness;
- Admin full inventory plus app-safe projection: authenticated product/operator consumption with separate DTOs.

The readiness CLI is an operation/inspection tool, not another long-running service. Its online mode queries the current manager/API. Its offline evidence mode may read a runtime-produced audit snapshot and use the shared Go inspector/evaluator to validate schema, identity, generation and freshness for `SurfaceReportV1`; that result is evidence only and can never seed startup, `Require` or another runtime authorization decision.

## Snapshot and Evaluation Architecture

### Observation model

Each probe result should contain a stable dependency/probe ID, affected capability IDs, availability, structured reason code, observation time and sanitized detail. The manager derives the probe set only from capabilities applicable to the selected profile; excluded capabilities and candidate topology assets have zero probe calls. Raw credentials, DSNs, internal response bodies and target evidence do not enter the snapshot. Probe errors become typed blocked observations; they are not omitted from a successful refresh candidate.

The evaluator joins immutable contract + selected profile + trusted identity + a complete observation set + current clock. It computes capability verdicts and `validUntil` from the oldest applicable observation. It also rejects identity/profile/generation inconsistencies and observations beyond future skew. Only this evaluated value is published.

### Bootstrap and refresh

Bootstrap can publish generation 1 even when non-DB dependencies are blocked, provided the contract, identity, profile, DB, migration ledger and observation set are structurally valid. This enables the operator control plane without enabling customer effects.

A refresh attempt builds a complete candidate off to the side. The periodic scheduler uses the authored `30s` interval and rejects any runtime attempt to replace it. Dependency timeout/error becomes a blocked observation and publishes a fresh generation so denial is immediate. Only a coordinator/evaluator/identity/schema failure that prevents a coherent candidate retains the previous pointer unchanged. Retention does not reset time; the old generation naturally becomes stale at its original `validUntil`.

### Publication and audit

An `atomic.Pointer` to an immutable snapshot matches the read-heavy guard path and avoids locks at every side effect. All maps and slices must be cloned/frozen before store. Tests should race many concurrent `Require` calls against refresh and run under `go test -race` for the package.

Audit serialization follows publication and writes typed `ReadinessSnapshotV1` through a shared atomic-file primitive. A write failure is visible to operator/release evidence but never causes a runtime read fallback. The HTTP views call `Evaluate` on the manager and therefore continue to report the in-memory truth even when filesystem export is unavailable.

Phase 31.1 registers two distinct schemas in the Phase 31 `surfacereport` registry. The readiness `evidence.details` shape contains exactly `generation`, `checkedAt` and `validUntil` for the minimum contract; the Go inspector validates an online evaluation or offline runtime-produced snapshot, reuses the same evaluator for freshness, and writes the readiness `SurfaceReportV1`. The deployment schema is owned by the disposable harness and records the explicit profile, canonical workload/probe/audit wiring and identity-bound harness result as typed stable values. It emits a separate deployment report. Arbitrary details, missing required keys, Python-side freshness calculations and readiness/deployment report folding all fail.

## Startup Refactor Direction

The current `NewServer` should be divided into a side-effect-free build phase and an explicit background start phase. `main.go` should synchronously open a listener before starting refresh/workers so bind failures cannot leave workers running without a control plane. One viable lifecycle is:

```text
load/validate contract + selected profile + trusted build identity
open and ping DB
apply migrations and validate ledger
construct bounded probes and readiness manager
bootstrap and publish generation 1
construct router/server with guard and manager views
open listener and start Serve
start periodic refresh and background workers under shutdown context
```

Relay health checks currently started inside the constructor may remain a diagnostic input, but they cannot become a second authorization source. Prefer moving their lifecycle into the explicit background owner and adapting bounded current-state checks into manager probes.

## Catalog Authority

`catalogBindings` should compile into immutable lookup tables during contract load. Lookup keys must include subject kind and the runtime discriminator needed to distinguish builtin, custom and MCP tools. A request DTO containing `capabilityId` must be rejected as an unknown/forbidden field rather than silently trusted.

Mutation paths resolve the submitted model/tool/routing subject, require its capability, then persist only business identity/config. Read paths may enrich response DTOs with the server-derived capability. Execution paths always resolve again from persisted subject and current contract, then guard immediately before effect. This closes stale rows created before Phase 31.1 and prevents a malicious caller from selecting a more permissive capability.

## Validation Architecture

### Test framework

- Go table-driven unit tests for evaluator, manager, probes, startup ordering, guards, catalog and handlers, with every targeted regex executed through Phase 31 `scripts/run-go-tests-matched.sh` so zero matches fail.
- `go test -race` for snapshot publication and concurrent guard reads.
- HTTP/gRPC fake handlers and zero-call spies for denial before business dispatch.
- Shell/Python one-field mutation fixtures for audit/deployment evidence and unavailable-environment behavior.
- Existing deployment validation wrappers for Compose/Kubernetes canonical ownership.

### Required negative cases

- Missing/mismatched identity; missing/unknown/excluded profile; generation zero or rollback.
- Observation exactly at freshness boundary, one nanosecond stale, future boundary, one nanosecond beyond future skew.
- Fake-clock ticker proving no early refresh, refresh at authored `30s`, repeated cadence and rejection of request/env/runtime interval override.
- Hung or cancellation-ignoring probe proving bootstrap/refresh remains deadline-bounded and cannot publish a partial generation.
- Partial/failed refresh attempting to extend previous `validUntil`.
- Audit file seeded with enabled state before startup; runtime must ignore it.
- `ReadinessSnapshotV1` unknown/missing/identity-spliced fields, or readiness `SurfaceReportV1` details outside the registered `generation`/`checkedAt`/`validUntil` schema.
- Expected effect manifest vs Go static discovery vs runtime descriptor mismatch, including zero rows, missing/extra seam, duplicate descriptor, unknown capability and unclassified boundary.
- Excluded capability/profile or candidate asset attempting to register or run a probe; probe call count remains zero.
- Every HTTP/gRPC/worker/outbound/finance denial with downstream call count zero.
- Worker claim succeeds, generation expires, effect is denied while safe retry/release bookkeeping remains possible.
- Caller-supplied capability ID, stale persisted capability ID, unknown model/tool and runtime-class mismatch.
- App projection leaking excluded capability, dependency endpoints or raw probe details.
- `/livez` healthy while `/readyz` blocked, then stale without refresh.
- Missing Docker daemon or DB causing harness nonzero exit and cleanup, with no skip recorded.
- Compose/Kubernetes missing explicit profile, writable audit storage or correct live/ready probe split.
- Excluded standalone service or effectful operation tool attempting dependency/process/external dispatch; read-only inspector attempting audit-file authorization.

### Environment failure policy

Evaluator and guard unit suites require no external services. DB-backed startup tests use `TEST_DATABASE_URL` or an isolated disposable DB. The committed container harness requires both Docker and DB provisioning; absence is reported as failure. A developer may run narrower unit feedback without them, but that run cannot satisfy the Phase 31.1 completion gate.

### Identity-bearing two-stage proof

Evaluator, guard and deployment behavior can run in temporary clean Git fixtures during development (Stage A). Any row that compares binary, OCI label, packaged contract or runtime audit identity must then run after an atomic commit against that exact clean `HEAD` (Stage B). A later edit invalidates Stage B; only the exact passing commit may be pushed.

## Risks and Planning Guardrails

1. **Constructor leakage:** adding bootstrap in `main.go` while leaving goroutines in `NewServer` violates the startup contract. Split lifecycle ownership first.
2. **Guard only at ingress:** route tests can pass while retry or scheduled effects bypass expiry. Maintain a machine-checkable effect inventory and zero-call tests.
3. **Frozen generation permission:** passing a snapshot through a long workflow can authorize future steps after expiry. Each effect reads current manager state.
4. **Audit-file authority regression:** an inspection CLI or second process may be tempted to read JSON. File readers are prohibited for authorization; use manager/API or a fresh inspector evaluation.
5. **Catalog trust confusion:** response `capabilityId` can leak into request types or persistence. Mutation rejects it; execution resolves current bindings again.
6. **Liveness/readiness collapse:** a blocked dependency must not cause liveness restart loops, and a live process must not be marked ready.
7. **Second deployment authority:** patching both Kubernetes Deployments independently guarantees drift. Keep one canonical source and validate ownership.
8. **Evidence inflation:** a successful disposable harness is E2 only. Target clusters, external providers and signed artifacts remain later phases.

## Recommended Plan Decomposition

The phase fits eight ownership-bounded plans:

1. evaluator, immutable snapshot, manager/guard lifecycle, catalog resolver and effect-registry primitives;
2. startup ordering, control-plane health, read-only inspection/effectful operation boundary and audit export;
3. HTTP/gRPC guards, Admin/app and catalog request/response projections, and runtime effect inventory;
4. schedule/channel/batch/archive worker claim/effect guards;
5. Relay/Chat Provider and model dispatch guards;
6. MCP/Agent tool/channel dispatch plus catalog mutation/execution re-resolution;
7. checkout/refund/payout/settlement finance guards;
8. Docker/Compose/Kubernetes wiring, completeness verification and disposable E2 harness.

Plans should keep manager contracts stable before parallel consumers begin. HTTP/gRPC and worker plans may share a wave only with disjoint file ownership; tool/catalog and finance may share a later wave under the same rule. Relay/Chat remains a separate prior wave because its server/provider wiring overlaps both families. Each plan stays at two or three tasks and at most nine files.
